# 0.9.0 — 2026-10-15

## Added

- **`upstream_rate_limited`** ([#49](https://github.com/cyanheads/met-museum-mcp-server/issues/49)) on every tool: a retry ladder that ends on HTTP 429, or meets a `Retry-After` longer than the backoff cap or the call's remaining budget, fails as `RateLimited` (`-32003`) with `data.status`, the raw `data.retryAfter` when sent, a message naming the requested wait, and a wait-then-send-fewer-requests recovery. A `Retry-After` that fits is still waited out.
- **`met_get_object` `remainingIDs`** ([#50](https://github.com/cyanheads/met-museum-mcp-server/issues/50)): the distinct IDs past the first 20, in request order and never requested, with a `notice` and their own section in `content[]`. Absent at 20 or fewer.
- **`reign` and `portfolio`** ([#51](https://github.com/cyanheads/met-museum-mcp-server/issues/51)) on every `met_get_object` record, `''` when absent, rendered as `**Reign:**` and `**Portfolio:**` (`Joint reign of Hatshepsut and Thutmose III`, `Birds of America, plate LXXI`).

## Changed

- **Breaking: a `met_get_object` batch that fetches nothing and has a fetch end on HTTP 429 fails as `upstream_rate_limited` (`-32003`)** ([#49](https://github.com/cyanheads/met-museum-mcp-server/issues/49)) instead of `all_failed`, or `upstream_unavailable` beside a 5xx outage (both `-32000`); a firewall block and an all-404 batch keep their reasons. Read `data.reason`, `data.status`, and `data.retryAfter`. `met_list_departments`, `met_search_collections`, and `met_list_objects` keep `-32003` and gain the reason.
- **`met_get_object` `objectIDs` accepts up to 500 entries** ([#50](https://github.com/cyanheads/met-museum-mcp-server/issues/50)), one full search or list page. The first 20 distinct IDs are fetched and the rest come back in `remainingIDs`; a batch that throws names how many went unrequested.
- **`limit` up to 10,000 on `met_search_collections` and `met_list_objects`** ([#50](https://github.com/cyanheads/met-museum-mcp-server/issues/50)): a value above 500 reads a 500-ID page, and when IDs remain past it the `notice` says so and to continue from `nextOffset`.
- **Framework input repairs reach these tools** (mcp-ts-core 0.13.14): numeric and boolean strings (`limit: "600"`, `isHighlight: "true"`), a lone string for an array (`geoLocation: "France"`), a numeric string inside `objectIDs` (`["15"]`), and `null` at an optional key. A bare number for `objectIDs` is still rejected.
- **Fetch-error messages name the Met origin, not the URL path** (mcp-ts-core 0.13.12), and `ctx.log` records label the endpoint (`search`, `objects`, `object`, `departments`, `image`) instead of carrying request URLs.
- **Tooling**: `framework-skills/` and `scripts/check-framework-antipatterns.ts` sync to mcp-ts-core 0.13.15 (the antipattern gate's whitespace match now fires on macOS); `.env.example` carries the 0.13.15 framework block.
- **Docs**: README and `docs/design.md` cover the new reason, field, and caps and record Decisions #23 and #24; the `CITATION.cff` abstract swaps its em dash for a colon.

## Fixed

- **`met_get_object` stops feeding a 429 throttle** ([#49](https://github.com/cyanheads/met-museum-mcp-server/issues/49)): once a fetch ends on 429, IDs not yet started fail unrequested, capping a throttled batch at `MET_BATCH_CONCURRENCY` requests with a long `Retry-After` and `MET_BATCH_CONCURRENCY` × 4 without one. A throttled ID's `failed[]` entry carries the rate-limit recovery, not "Retry after a brief delay."
